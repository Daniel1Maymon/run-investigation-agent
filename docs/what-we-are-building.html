What we're building

The Run Investigation Agent, and what "skeleton" means.

1What a skeleton is

The smallest version of the project that runs from start to end, but doesn't do the smart part yet.

🏗️ House frameWalls, doors, and pipes connected to the street. You can walk from the front door to the kitchen, and the tap works. Nobody lives there yet.
🛋️ Furniture, laterWhat makes it a home. It goes in once the frame is solid.

In our project, the frame is a small web server that fetches a run from your trace viewer and hands it back. The furniture is the AI agent that reads the run and writes a diagnosis. That comes later.

2Why start with a skeleton

When the AI part goes wrong later, we want to know it's the AI and not the plumbing. The skeleton answers the boring questions first:

  1. Can our code reach the trace viewer on the Hetzner server?
  2. What happens when the tunnel is closed?
  3. What happens when someone asks for a run that doesn't exist?

3The finished product

You give it one run ID. It gives back a short report:
  • Did the task succeed, fail, or is there not enough evidence?
  • What went wrong, pointing at the exact message or tool call.
  • What to check or fix next.
It only reads. It never changes anything on the server.

5What the skeleton can do today

GET /health: "Are you up, and can you reach the viewer?"

Tunnel open"status": "ok"
Tunnel closed"status": "degraded" plus a hint to run dash. No crash.

GET /runs/<run id>: "Give me this run."

The run existsYou get the run back
The run doesn't exist404, "not found"
Tunnel closed503, "viewer unavailable", plus a hint to run dash

7What comes after the skeleton

  1. Data: the two tools, plus a saved copy of one real run.
  2. First investigation: connect the agent loop and a model, give it a run ID, and get a report.
  3. Visibility: log what the investigator did, how long it took, and what it cost.
  4. Evaluation: test it on a run that worked, a run that failed, and a run with missing data. We write the expected answers first.
