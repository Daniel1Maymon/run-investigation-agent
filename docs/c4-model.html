What we're building

An AI agent is a program that uses an AI model to do a task on its own. It reads a request, decides what steps to take, and uses tools like sending a message or reading a file. Each time it does a task is called a run, and everything it did during the run is recorded.

When a run goes wrong, a developer has to read that record by hand to find out why. That's slow.

This project is an investigation agent: an AI agent whose job is to investigate another agent's run. You give it the ID of one run. It reads the record and reports:

  1. Did the task actually work?
  2. If not, what went wrong, pointing at the exact message or step.
  3. What to check or fix next.

It only reads. It never changes anything. The agents it investigates run on OpenClaw, an agent platform. It gets their records from an existing tool called the trace viewer.

Where we are: it works end to end. You press Investigate on a run, the AI model reads the run through three tools, and hands in a checked report. Next comes evaluation: testing it on runs where we already know the right answer.

Level 1

Context

Who uses it, and what does it talk to?

Our whole system is one box. No technology, no files. Just the people and the outside systems around it.

  • It only reads. Nothing in this picture lets it change OpenClaw or the server.
  • The trace viewer already existed. We reuse it instead of reading the raw files ourselves.
  • The AI model decides what to look at and writes the diagnosis. The default is deepseek/deepseek-v4.1-flash; two other cheap models can be swapped in with one setting. (Decision record 0006.)
Level 2

Containers

What runs, and where?

Zoom into the boxes. A "container" here is anything that runs on its own or stores data: an app, a server, a database. (It has nothing to do with Docker containers. Same word, different meaning.)

Engineering choice: our app talks to the viewer over HTTP instead of opening the database itself. The viewer already knows how to rebuild a run from those files, so we don't copy that code. And it works from the Mac through the same tunnel you already use. (Decision record 0001.)

  • If the tunnel is closed, our app can't see any runs. That's why /health reports "degraded" and tells you to run dash.
  • The page is one plain HTML file served by the API itself (0002). It refreshes the session list on its own, but only when the viewer says its data changed (0010).
  • The API key lives in .env, which is never committed.
Level 3

Components

What are the parts inside our app?

Zoom into just the Investigation API. Each box is one part with one job. All of them are built.

Engineering choice: only the adapters know the outside world. The OpenClaw adapter is the only part that knows OpenClaw's format; the model adapters are the only parts that know a provider's API. The loop and the tools only see our own shapes. To investigate a different agent system, you write a second OpenClaw-style adapter; to try a different provider, a second model adapter. Nothing else changes. (0004, 0005.)

  • The model has three tools. Two are in tools.py. The third, submit_report, is how the model finishes: its input is the report, and the loop checks it. Its schema is generated from Report in schema.py, so the shape is defined in one place (0009).
  • The run is downloaded once per investigation. The tools only cut that copy down, so the evidence can't change while the model works (0008).

Code

Which functions run, in what order?

The closest zoom. The C4 model says this level is optional, since the code itself shows it. Here is one investigation, POST /runs/{run_id}/investigate, followed through the real functions, top to bottom.

That's the happy path. An investigation can end in three ways, and the page shows which:

StatusWhenWhat you get
doneThe model called submit_report with a valid report.The report and every step.
stoppedOur limits: 12 model calls or 180 seconds.The steps so far and the reason. No report.
errorA model call failed (for example, the provider was down).The steps so far and the error. Still HTTP 200: the investigation answered, it just didn't finish.

Before the loop starts, the viewer can also say no. The adapter turns each answer into a clear result:

Viewer saysAdapter doesYou getWhy
200 + runreturns it unchanged200Normal case.
404raises RunNotFound404A wrong ID is a normal answer, not a crash.
500, or no answerraises ViewerUnavailable503Our app is fine, but the thing behind it isn't. The message says "run dash".
  • Every reply from the model goes back into the history, so on the next call the model sees everything it asked for so far.
  • If the report is invalid (wrong shape, or it cites an event that doesn't exist), the loop answers the submit_report call with an error saying what's wrong, and the model fixes it, like a bad get_event. Plain text with no tool call is not accepted as a report.
  • In the tests, both the viewer and the model are swapped for fakes, so all 99 tests run without the server, the tunnel or an API key. A live run through the tunnel checks the real path.
